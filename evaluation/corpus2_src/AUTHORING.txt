AUTHORING BRIEF - second (held-out) corpus, doc-201 .. doc-260
================================================================
Six authors each write one batch file of 10 documents. This file is the shared brief.

FILES AND COMMANDS (run from the repository root; keep commands short; never use the bare word "eval")
  your file     evaluation/corpus2_src/batch_<x>.py      (x = a..f; the ONLY file you create or edit)
                starts with:  from corpus2_src.core import D, dt, amt, num
                              DOCS = []
                              BATCH_COMMON = []   # optional, see LEFTOVERS
  build         python3 -P evaluation/generate2.py --batch <x>          -> evaluation/corpus2/.work/<x>/
  verify        python3 -P evaluation/verify_corpus2.py --corpus evaluation/corpus2/.work/<x>
  mint numbers  python3 -P evaluation/generate2.py --mint card -n 8 --salt <x>1
                (kinds: card iban aba sin ssn imei; always use a salt starting with your batch letter)
  Do NOT edit core.py, common.py, generate2.py, verify_corpus2.py or another batch. Do not read taxonomy/, src/,
  bench/, tools/, evaluation/RESULTS.md, evaluation/results/. No git. No /tmp. If a tooling bug truly blocks
  you, stop and report it instead of patching the tooling.
  DONE = build prints "0 errors" for your batch AND verify prints "0 mismatches, 0 unreviewed leftovers".
  Markup, D(...) fields and renderer features: read the docstring at the top of core.py (already in context).

SIZE TARGETS
  normal doc 150-600 words and 50-75 key items; long doc 1,200-2,500 words and 140-200 items; short doc under
  80 words and 12-20 items. Batch total roughly 620-720 items. xlsx: 2+ sheets where sensible, real date and
  currency cells via dt()/amt()/num().

WRITE LIKE REAL PEOPLE
  Real business documents: letterheads, signature blocks, reference lines, abbreviations, shorthand, typos that a
  busy person would leave, inconsistent formats inside one document (a phone written three ways, a name as
  "Last, First", initials, ALL CAPS in captions, nicknames, title + surname), amounts as $1,250.00 / 1250 / 1.25k
  / "twelve hundred" / (450.00) / USD 3,000, dates as 03/04/26, 4 Mar 2026, March 4th, 2026-03-04, "the 4th",
  "Mar-26", numbers with and without separators, masked and last-four forms, unlabelled IDs, look-alike traps
  (a surname that is a common word or a place, a city that is a first name, a 4-digit last-four that looks like a
  year). Go beyond the subtype range of the first corpus (listed earlier in context) rather than repeating it.
  Include plenty of ordinary non-sensitive content and look-alikes: statute and regulation cites, form numbers,
  section numbers, CPT/ICD codes used generically, product and software names, generic public bodies. List the
  look-alikes in distractors=[...] (at least 3 per document, each must appear verbatim in the text).

FICTIONAL DATA RULES
  Everything invented. No real private individuals; no real companies as parties, banks, insurers, clinics or
  employers (real software/products, card brands and government bodies may be mentioned and are distractors or
  ok entries). Real cities/states are fine; street addresses invented. Emails/URLs only on .example or
  example.com|org|net. US/Canada phones 555-01xx (any area code); UK 01632 960xxx / 020 7946 0xxx / 07700 900xxx;
  other countries clearly fictional. Cards pass Luhn, IBANs mod-97, ABA routing checksum, Canadian SINs Luhn
  (subtype must contain "SIN"), SSNs plausible (mint them). IPs only 192.0.2.x, 198.51.100.x, 203.0.113.x,
  10.x, 172.16-31.x, 192.168.x, 2001:db8::/32, fd00::/8, fe80::. The build enforces all of this.
  NOVELTY: the build rejects any person whose surname (or hyphen part) appears in the first corpus and any
  organization whose leading word matches a first-corpus organization. Pick fresh names from many cultures.
  New storylines only; nothing adapted from the first corpus.

CATEGORIES (exactly these 29; aliases in core.py ALIAS)
  person_name organization_name email phone street_address postal_code place ssn tax_id government_id
  bank_account routing_number iban payment_card card_expiry card_security_code money_amount date_of_birth date
  age_over_89 record_number url ip_address vehicle_id device_id credential health_info sensitive_attribute
  indirect_identifier

KEYING CONVENTIONS (apply uniformly)
  person_name       every written form (full, short, title-surname, first-name, surname, initials, caps,
                    last-first, nickname). Include the honorific in the value when it is written with the name.
  organization_name parties, employers, firms, banks, insurers, clinics, schools, churches, unions, trusts,
                    estates. NOT government bodies, courts, software, card brands (distractor / ok).
  street_address    the street line incl. unit/suite/PO Box. City, state/province and postal code are separate
                    items (place, place, postal_code). A place inside an organization name or statute name is not
                    separate.
  place             city, town, county, state/province (also abbreviations), neighbourhood, named facility,
                    foreign city. Countries only when they locate a person abroad.
  date              every specific date tied to the matter (full, partial, month+year, month+day, "the 14th").
                    NOT keyed: bare years, bare month names, durations ("30 days"), clock times, percentages,
                    quantities, ages under 90, tax years. Birth dates -> date_of_birth (a bare birth year too, hard).
  money_amount      every specific amount incl. rates and totals, in whatever notation.
  record_number     matter/case/docket/invoice/claim/policy/loan/MRN/member/employee/check/Rx/order numbers.
  government_id     passport, driver's licence, bar/licence/NPI/DEA numbers, A-number, health card, Medicare MBI.
  tax_id            EIN, ITIN, PTIN, SIN, BN, VAT, UTR, state tax account numbers. SSN always -> ssn.
  bank_account      account numbers (also brokerage, masked, last four), SWIFT/BIC.
  routing_number    ABA, Canadian transit/institution, UK sort code.
  payment_card      full, masked or last-four card numbers; put the holder's entity id in cardholders=[...].
  credential        usernames, passwords, PINs, security answers, tokens, door/lockbox/alarm codes, Wi-Fi keys.
  device_id         serial numbers, IMEI, MAC, hostnames, asset tags.      vehicle_id  VIN, plates, hull numbers.
  health_info       diagnosis, medication, lab value, procedure, allergy, symptom tied to a person (minimal phrase).
  sensitive_attribute  race/ethnicity, religion, orientation, gender identity, immigration/citizenship status,
                    criminal history, union membership, political activity, financial distress, benefits status.
  indirect_identifier  phrases that single a person out without naming them (unique role, relationship to a
                    named person, distinctive asset, school + grade).
  age_over_89       ages 90 and above, however written.
  minors=[...]      entity ids of every person the document shows is under 18 (by birth date, age, grade or
                    wording). cardholders=[...] entity ids of every named holder of a card in the document.
  The same string is one item counted everywhere it occurs: mark it once (re-marking is harmless), and make sure
  the identical string is not also used with another meaning. Values must sit on one line and cannot contain "|".
  In PDF documents keep table cells short (a wrapped cell breaks the text layer) or avoid tables.
  In raw_html documents keep sensitive values out of attributes and comments.

DIFFICULTY - one rule
  hard = masked or partial numbers, numbers without their usual separators, values spelled out in words, ALL CAPS
  names, initials/acronyms, nicknames, names that are also common words or places, "Last, First" order,
  unlabelled IDs, and all health_info / sensitive_attribute / indirect_identifier. The build marks the
  mechanical cases automatically (caps, initials, acronym, last-first, nickname, masks, digit-only ssn/card/
  phone/tax id, last-four, spelled-out amounts and dates, the three always-hard categories). YOU add "!" for the
  rest: names that are common words or places, unlabelled IDs, digit-only forms of other categories, partial
  values the automation cannot see. Do not add "!" for anything else.

LEFTOVERS (completeness review - this matters most)
  The build lists, per document, every capitalised word, every token containing a digit and every email/URL-
  looking token that is not inside a key value or a distractor. For each one decide honestly:
    sensitive            -> mark it in the text;
    look-alike           -> distractors=[...] (phrases such as "Form 1040-ES", "Schedule K-1", "Cal. Civ. Code § 1950.5");
    ordinary             -> ok=[...] of that document (exact token as printed, or a phrase containing a space).
  A generic word you keep needing can go once into BATCH_COMMON (lower case). Never put there: month names, or
  any word that doubles as a first name, surname, bank or place. Two-letter ALL-CAPS tokens always need ok.
  Never use ok to hide something that belongs in the key.

FINAL REPORT (short): per document id: words, items, minors y/n, cardholders y/n; batch item total; anything you
could not do or are unsure about. State the last line printed by build and by verify, verbatim.
